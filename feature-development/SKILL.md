# Feature Development

这个文档用于新功能开始开发前的基础项目管理。

当一个 Feature 已经确定要做时，根据当前功能需求和项目现状，拆解完成该 Feature 所需要的主要工作，并评估工作量、依赖关系和整体排期。

这里不负责详细设计 Feature，而是回答：

> **这个功能要做哪些事情，大概要花多少时间，应该按什么顺序推进。**

---

## 使用口径

- **用户与 Agent 协作。** 默认由 Agent 承担技术执行，用户负责产品、交互和 UI 的最终选择以及最终体验验收；具体边界见下节。用户仍是一位独立开发者，不默认存在多个团队，也不额外引入团队管理流程。
- **并行与时间。** 分别估算 Agent 执行时间与用户投入，不把全部工作量都算作用户人天，也不套用固定的 AI 提效倍数。只有实际可独立推进的工作才可穿插，例如用户审阅期间 Agent 处理已确定的独立工作；依赖用户选择的工作需等待相应确认。自然排期另外考虑双方可投入时间、反馈等待、工具运行和必要修改。没有开始日期或投入安排时，给相对顺序和带前提的区间，不编造具体完成日期，也不暗示 Agent 会在会话之外自动持续工作。
- **带假设出初稿。** 优先使用当前对话和已提供的项目资料。信息不足时，列出假设和影响范围或排期的待确认项，先给粗略计划，不要求提前完成详细设计。缺少功能描述等无法合理假设的关键信息时，先集中询问。

## 执行与最终把关

- **你最终把关。** 产品取舍、交互方案选择、UI 最终判断，以及最终测试效果和体验验收，由用户确定。Agent 可以整理选项、提出建议、准备原型和验收材料，不替用户宣布接受。
- **Agent 执行。** 技术相关工作默认交给 Agent，包括查官方文档、梳理 API 限制、技术预研、写代码、准备测试矩阵、运行可执行的检查、检查字符串和多语言一致性、修复问题及更新文档。按任务需要列工作项，不把这些示例都变成必做项；本阶段只规划，不实际展开完整测试矩阵或开始开发。
- **技术检查与体验验收分开。** Agent 说明检查结果和实际验证边界；用户确认最终效果。需要用户操作设备、账号或目标 App 的步骤，单列用户实际操作时间，不把整个技术测试工作转交用户。未实际执行的场景不得记为通过。
- **在表内落地分工。** 保留原表列名，在“主要内容”中使用“Agent……”和“你……”表述各自动作；在“完成标志”中写明技术产物或检查通过，以及确实需要的用户最终确认。技术执行项不必逐项等待用户批准，产品和体验把关节点应明确。
- **明确暂时不做。** 本次排除的内容进入 Deferred，不分配执行工作量；本次验收所必需的异常处理不能借此移出范围。
- 用户明确指定纯人工估算或其他分工时，按本次要求调整。

## 目标

每次规划一个 Feature，需要明确：

1. 需要完成哪些主要工作？
2. 每项工作大约需要多少时间？
3. 哪些工作有前后依赖？
4. 哪些工作可以并行？
5. 整个 Feature 预计需要多久？
6. 每个阶段做到什么算完成？
7. 哪些环节最可能增加工作量或导致返工？
8. 哪些内容本次明确暂时不做？

## 最终交付

最终以一张项目管理表为主要交付物。

| 阶段 | 工作项 | 主要内容 | 工作量 | 依赖 | 建议排期 | 完成标志 | 主要风险 |
| -- | --- | ---- | --: | -- | ---- | ---- | ---- |
| 方案 |     |      |     |    |      |      |      |
| 设计 |     |      |     |    |      |      |      |
| 开发 |     |      |     |    |      |      |      |
| 完善 |     |      |     |    |      |      |      |
| 验收 |     |      |     |    |      |      |      |
| 发布 |     |      |     |    |      |      |      |
| 文档 |     |      |     |    |      |      |      |

表格中的阶段根据 Feature 实际情况调整，不要求机械保留所有分类。

工作项保持在项目管理粒度。

例如：

- 产品范围定义
- 技术预研
- 产品逻辑
- UI / 交互设计
- 主流程开发
- 状态及异常处理
- 真机验收
- 多语言
- 发布准备
- 文档同步

不要进一步展开到具体页面、具体 API、具体代码文件或逐条测试 Case。

## 整体评估

项目管理表之后，补充一份简短的整体评估：

| 项目               | 评估    |
| ---------------- | ----- |
| 总工作量             | Agent X～X 小时；你 X～X 小时 |
| 建议自然排期           | X～X 天 |
| 第一个里程碑           |       |
| 第二个里程碑           |       |
| Feature Complete |       |
| Release Ready    |       |
| 最容易超期的部分         |       |
| 可以并行的工作          |       |

### 工作量估算

按人天估算时，优先使用以下粒度；Agent 协作中的小时级任务直接使用小时：

- 0.25 天
- 0.5 天
- 1 天
- 1～2 天

存在明显不确定性时使用区间，不给出虚假的精确时间。

区分：

**总工作量**

分别列出 Agent 执行时间与用户投入时间，并核对表内合计。Agent 时间包括实现、工具执行、构建检查及修复迭代；用户时间包括必要决策、审阅、设备操作和最终体验验收。小时级任务优先使用小时；采用人天时说明每天有效投入小时数。双方时间不直接相加为自然排期。

**自然排期**

考虑依赖关系、并行工作、验收和返工之后，从开始到 Release Ready 大约需要多少时间。

两者不一定相同。

---

## 排期原则

排期应该体现真实工作顺序，而不是简单把所有任务串行排列。

优先识别：

- 哪些工作可以同时开始
- 哪些工作必须等待前置任务完成
- 哪些工作可以在主流程开发后处理
- 哪些工作需要预留验收和修改时间

例如：

> 产品定义与技术预研可以并行。\
> UI 设计需要等待关键技术限制确认。\
> 多语言和文档更新可以等 Feature 基本稳定后再进行。

---

## 里程碑

根据 Feature 实际情况定义少量关键里程碑。

通常可以参考：

### 方案确定

产品范围、关键技术限制和设计方向已经明确。

### 主流程可运行

Feature 核心功能已经可以实际运行。

### Feature Complete

计划范围内的功能、主要状态和必要异常处理已经完成，可以进入最终验收。

### Release Ready

Agent 已完成验收问题修改、多语言、兼容性检查和必要文档，用户已确认最终测试效果与体验验收，可以进入发布流程。构建或自动检查通过不能替代用户的最终验收；仍待用户验收时，明确标记为待验收。

不要求每个 Feature 都机械使用这四个里程碑。

---

## Deferred

明确写出本次暂时不做的内容。

目的是防止开发过程中 Feature 范围持续扩大。

只需要列主要项目，不展开讨论。

例如：

- 更复杂的自定义能力
- 非核心状态
- 后续版本才需要的数据统计
- 暂时没有必要支持的平台或系统版本
- 可以后续优化的视觉细节

---

## 风险

只记录可能明显影响项目排期的事项。

例如：

- Apple / 第三方 API 能力尚未确认
- 必须使用真机才能验证
- 涉及现有核心模块修改
- 产品状态较多
- 设计方案存在较大不确定性
- 与其他正在开发的 Feature 有依赖
- 验收阶段可能暴露此前没有定义的场景

不要把普通开发工作全部列成风险。

---

## 边界

这个阶段只负责基础项目管理。

不要在这里详细展开：

- 完整 PRD
- 详细产品逻辑
- 每个状态的具体交互
- UI Spec
- API / Architecture 设计
- 具体代码实现
- 文件级开发任务
- 完整 Test Matrix
- 详细多语言文案

这些内容在对应工作开始时，通过独立对话继续处理。

如果某项工作需要进一步讨论，在项目管理表中只需要把它识别为一个工作项，并估算对应工作量。

---

## 最终原则

项目计划的重点不是提前把 Feature 的所有细节设计完。

而是让开发开始之前能够清楚看到：

> **要做什么 → 各自需要多少工作量 → 哪些有依赖 → 怎么安排 → 做到什么算完成 → 整体什么时候可以结束。**

最终输出应该让人一眼看懂这个 Feature 的项目全貌和进度结构。
